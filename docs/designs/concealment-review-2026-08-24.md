# Review: reputation ledger + wiki concealment (f15f0a3b..d081958d)

**Adversarial five-lens review, 2026-08-24.** 58 findings survived verification. Kept in the
repo because several are the kind that only a fresh reader sees: claims in commit messages and
docstrings that the code does not support. Items are struck through in this file as they are
fixed.


## 1. Ship or not

Merge it — but not on the strength of the stub, and not with the commit messages as written. The stub does make most of the concealment defects latent, and that is real. What it does not cover is three things that are live on `main` the moment this lands: `LocationWikiEditDeleteView` no longer erases the data it promises to erase (`WikiFieldRevision` keeps the pasted string and the actor, with no purge path); every external-API write now records `source=system, actor=NULL` because `WriteSourceMiddleware` runs before DRF authenticates; and two of the six reputation rules cannot fire from the path their subscription targets, so the calibration data the stub is explicitly waiting on is being collected wrong from day one. Fix those three and the substrate is safe to sit behind the predicate. But the flip is not "a change to one function" — `concealed_field_values` and `conceal_rows`, the two functions that actually conceal anything, have **zero** production callers. Flipping the boolean today hides the pin count, the stat votes and the boundary dialog, and keeps rendering the name, description, dates, security chips, comments, images, aliases, links and the entire edit history that strangers wrote. The docstring at `concealment.py:145-148` is the single most dangerous line in the branch, because it is the line the person who eventually flips the switch will read instead of grepping.

## 3. Should fix

- **`versioned.py:232-252` — the recorder has no savepoint, so swallowing the error poisons the caller's transaction.** `bulk_create` is wrapped in a bare `try`/`except Exception`, with no `transaction.atomic()` of its own. On PostgreSQL a failed INSERT aborts the transaction at the server; catching the Python exception does not clear that, so the next statement in the caller's `atomic()` block raises. (Note: the mechanism is the server-side abort, *not* `needs_rollback` — Django's `bulk_create` only opens `atomic(savepoint=False)` and only when there are both pk'd and pk-less objects, which never holds here, and nothing calls `mark_for_rollback_on_error` on this path. A fix keyed on `needs_rollback` would miss.) Callers inside a transaction: `wiki_creation.py:88`, `pin_wiki_sync.py:168` and `:224`, `pin_restructure.py:565`, `external_api/views_wiki.py:249`. The codebase already knows this trap — `wiki_aliases.py:94-98` and `pin_subresources.py:166-170` both open a nested `atomic()` purely for the savepoint, with comments explaining why. Do the same inside the `try`. Also move `revision_model = _revision_model(model)` (`:228`) inside the `try` while you are there — `apps.get_model` raises uncaught.

- **`versioned.py:255-261` — `concrete_field` raises `FieldDoesNotExist`, so both `is None` guards are dead.** `Options.get_field` raises for an unknown name and returns a non-`Field` only for a reverse relation, which can never appear in the table (names come from `versioned_fields` or update kwargs). Consequence: `field_name` is historical text in an append-only table, so the first rename or drop of a versioned field turns every `resolve_fields` call on a wiki carrying an old row into an uncaught 500 on the concealed render path. Catch `FieldDoesNotExist` and return None — that makes the docstring true and both guards (`versioned.py:330-332`, `concealment.py:127-129`) live.

- **`versioned.py:164-168` — the `from_db` snapshot makes `.only()`/`.defer()` infinitely recursive.** It `getattr`s all 14 versioned fields on load; `DeferredAttribute.__get__` calls `refresh_from_db(fields=[...])`, which builds `.only(*fields).get()` through the same `from_db`, whose snapshot loop hits a different deferred field. States alternate with one query per frame until `RecursionError`; `getattr(..., None)` only absorbs `AttributeError`. Latent — no `Wiki` call site uses `.only()`/`.defer()` today. Build the snapshot from `field_names`/`values`, or intersect with `set(field_names) - get_deferred_fields()`.

- **`versioned.py:170-195` — `refresh_from_db()` leaves `_version_snapshot` stale**, so the next bare `save()` diffs refreshed values against pre-refresh ones and attributes another writer's changes to the current actor — the precise re-attribution the docstring at `:170-179` says it prevents. Relatedly, `Wiki(pk=<existing>, ...)` never passes through `from_db`, so `snapshot is None` sends it down the create branch and records all 14 fields. Treat "no snapshot but `pk` set and not `_state.adding`" as unknown, not as create.

- **`versioned.py:134-142` — `bulk_update()` double-records, half the rows storing a `Case` repr.** Verified against this venv's Django 6.0.6: `query.py:961-963` ends `bulk_update` with `queryset.filter(pk__in=pks).update(**update_kwargs)` on a clone of the same class, so it re-enters the override. `update_kwargs` is keyed by `field.attname`, which equals the declared name for all 14 of Wiki's versioned fields, so `touched` matches and `_serialise` falls through to `str(value)` on a `Case` expression — the stored text is `"CASE WHEN … THEN …, ELSE …"`. Lines 141-142 then record the real values at higher pks, which is the only reason resolution currently lands correctly. The test at `test_versioned_fields.py:58-63` uses `assertIn` on a list and cannot see it. Guard the inner call with `unversioned()`, and make `_serialise` refuse anything with `resolve_expression`.

- **`bin/check_versioned_writes.py` is registered nowhere.** Not in `.pre-commit-config.yaml` (which wires `imports-tracked`, `outage-not-cached`, `notification-choke-point`), not in `.github/workflows/ci.yml` (which runs `check_imports_tracked`, `check_doc_line_refs`, `check_migration_graph`), not in `pyproject.toml` or `package.json`. Separately, its rename check cannot fail for `Wiki`: `_declared_fields` (`:71-79`) counts *any* class-body call assignment, so DRF serializer fields and Pin's own columns feed `_ALL_FIELD_NAMES` — I re-ran its AST logic and every one of Wiki's 14 versioned names appears elsewhere (name 76×, description 26×, the rest 3-8× each). Problem class 3 from its own docstring is undetectable for the only model using the substrate. (`bin/check_pin_not_published_to_wiki.py` is also unrun.)

- **`services/wiki/wiki_edits.py:287` — `restore_event` can never fire.** The only writer clearing `WikiEdit.reverted` is `WikiEdit.objects.filter(pk__in=undone_ids).update(reverted=False, reverted_by=None)`, and `WikiEdit`/`WikiEditQuerySet` are plain `DashboardModel`/`DashboardQuerySet` — no `post_save`, no interception. `on_wiki_edit_reverted` is connected only as `post_save` (`signals.py:232`); `restore_event` has no other caller outside tests (`scoring.py:238`). ## 4. Overstated claims

1. **`concealment.py:145-148`:** *"Landing the mechanism behind a stub keeps every call site written and exercised in the meantime, so turning it on later is a change to one function rather than a sweep."* False, and it is the claim a future implementer will act on. `concealed_field_values` and `conceal_rows` have zero production callers; four surfaces are wired (viewed_by_other, community summary, stat composites, boundary dialog) and at minimum five are not (every field value on the HTML page, the security chips and the Suggest-edits prefill, the edit history, the entire external API payload, the alias/link/comment/image/floorplan row sets). b5982081's commit message does say "Nothing calls this yet"; the docstring says the opposite, and the docstring is what gets read.

2. **`concealment.py:151-153`:** *"Deliberately the* only *place this decision is made."* True of the predicate, not of the substitution — `wiki_detail.py` makes the opposite decision by omission for every API consumer.

3. **`location_wiki.py:130-133`:** *"Shared with the external API's wiki detail payload so the two can't drift on the privacy rules."* They have drifted: the concealed branch at `:137` was added on the HTML side only.

4. **`controllers/location_wiki.py:456-461`:** *"hard-deletes the WikiEdit row … so no copy of the data lingers anywhere."* No longer true as of f08ed3ed; the value and the actor survive in `WikiFieldRevision` with no purge path.

5. **`UrbanLens/celery.py:57-59`:** *"Deliberately not paired with a reset in `task_postrun`: each task runs in its own context."* `grep -rn 'copy_context\|contextvars'` over the installed celery 5.6.3 returns nothing. True of the prefork worker only; false for the eager path, which is a supported setting.

6. **`versioning.py:12-14` / `middleware.py:195-200`:** *"inside an authenticated request -> USER"*, with only "anonymous requests" falling through to SYSTEM. The external API is an authenticated request that lands in the anonymous branch.

7. **`versioning.py:16-17` and `celery.py:53-55`:** the documented `writing_as` override for "a task acting *for* a person" has no non-test caller — `writing_as` is used at `middleware.py:222` and nowhere else in `src/` or `bin/`. Meanwhile the *inverse* mis-classification is live (`claim_for_location` records provider data as USER). Either add the call sites or say the override is currently unused.

8. **`versioned.py:222-226`:** *"Never raises in production."* True of the Python exception, false of the consequence — inside a transaction, the caller's next query dies instead. The stated asymmetry only holds for non-database failures.

9. **`versioned-content.md:97-100`:** *"In production it records the revision anyway from the post-write state (degraded provenance, marked as such) and logs an error. ## 5. What I would test first

**Render the wiki page and the API payload with `concealment_active` monkeypatched to `True`, as a stranger, against a wiki a different user built — and assert absence, not presence.** One view-level test:

```
patch concealment_active -> True
GET /location/<slug>/wiki/  as a profile with no pin, no friendship
assert the stranger's name, description, security values, aliases,
       links, comments, images and edit-history entries are all absent
GET the external API's wiki detail for the same wiki, assert the same
```

That single test fails today for every unwired surface at once — it catches the `concealed_field_values`/`conceal_rows` no-caller gap, the API payload, the security chips, the Suggest-edits prefill, the edit history, the public-vote block, and it immediately surfaces the blank-name fallback as the concealed render's own tell. Every existing concealment test asserts on functions in isolation (`ConcealedValueTests` deletes the real creation revisions in `setUp` at `test_wiki_concealment.py:37` and hand-writes an AUTOMATIC row, so no test has ever seen the revision set a real wiki carries), which is exactly why the wiring gap survived a self-review.

Second, if there is room for one more: a real request through `WriteSourceMiddleware` (log in, POST a wiki edit through the URL, assert the `WikiFieldRevision` carries USER and that profile) plus the same edit through the external API. `grep WriteSourceMiddleware` returns only its definition and its `MIDDLEWARE` entry — the component that decides whether anyone can see their own edits has no test at all, and `test_a_write_during_a_signed_in_request_is_that_persons` (`test_versioned_fields.py:158`) calls `writing_as` by hand rather than issuing a request, so it asserts on the context manager, not the middleware.
