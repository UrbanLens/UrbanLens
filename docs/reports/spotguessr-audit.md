Assessment complete — I've now read every SpotGuessr module end-to-end (all 16 service files, models/querysets, controller, WebSocket consumer, the full TS entry, SCSS, templates, and the design doc). Here's my honest verdict.

Overall: the backend is genuinely well-built; the frontend and the "game feel" layer are where the real debt lives
What's done well (worth preserving as-is)
Layering is textbook. glicko2.py is pure math with zero ORM dependency; ratings.py wraps it in persistence; session.py orchestrates; the controller only does HTTP. Serializers are shared between HTTP and WebSocket so payload shapes have one source of truth. This is exactly the abstraction discipline the project's CLAUDE.md asks for.

The "why" documentation is exceptional. Nearly every non-obvious decision is written down where you'd trip over it: why boundary rounds deliberately don't snapshot geometry, why PhotoCoordinateGuess structurally can't be traced to a person, why session chat isn't E2EE, why the wiki-attachment gate is non-negotiable. Five years from now this feature will still be modifiable.

Concurrency and privacy are handled like production code. select_for_update around round completion prevents double-applied ratings; duplicate guesses are handled via the DB constraint, not a racy check; the answer is never serialized pre-reveal; multiplayer withholds the reveal from early guessers so chat can't leak it; 404-not-403 everywhere so sessions don't leak existence. Distance uses real PostGIS geodesic math instead of the codebase's known-approximate shortcut, deliberately.

Genuine game-design thought: anti-clustering (no two consecutive rounds within 500m), Gaussian difficulty weighting with a neutral prior for unrated locations, and the clever secondary data flywheel where gameplay crowd-sources photo coordinates and photo-quality signals back into the site.

Real gaps, ranked by how much I'd care
1. Multiplayer has a hard stall with no escape hatch (correctness, not polish). A round only completes when every joined participant guesses. If one player closes the tab, the round never reveals, ratings never apply, and the session hangs forever. GameSessionStatus.ABANDONED exists in the enum but nothing in the codebase ever sets it — there's no timeout, no "skip AFK player," no host ability to end the game. This is the one thing I'd call a must-fix before multiplayer gets real use.

2. The TS frontend is the maintainability liability. spotguessr.ts is a ~1,300-line hand-rolled SPA with ~15 module-level mutable variables (sessionId, currentMode, isMultiplayer, …) and a five-panel state machine managed by scattered .hidden writes — every render function must remember to hide every other panel. The [hidden] CSS bug I just fixed was a symptom of this: there's no single showPanel(name) chokepoint. It also has zero tests (the project has bun-test infra; map-layers.test.ts proves the pattern), and the TS payload interfaces mirror serializers.py by hand — my bonus_points addition needed synchronized edits in four places, which is exactly how drift bugs happen. A modest refactor (one panel-switch function, one state object, extract the duplicated ~30-line reveal-drawing block shared by showReveal/showBroadcastReveal) would pay for itself quickly. It's also worth noting this feature quietly abandons the project's HTMX-first philosophy — defensible for a game, but the lobby/scoreboard/summary panels are plain server-renderable lists that didn't need hand-rolled DOM building.

3. Extensibility: adding a fourth game mode is currently a scavenger hunt. Mode-specific logic is if/elif chains repeated in at least three places — round generation (session.py:281-304), serialization (serializers.py), and now the feedback gate. A small per-mode strategy (each mode declares: candidate-finder, scoring target, serialized payload, shows-imagery?) would collapse that to one registration per mode. Related small smell: GameSessionConsumer hardcodes the group-name string instead of calling realtime.session_group_name(), and TriviaSessionConsumer is an admitted copy-paste "exact mirror" — a shared base consumer would serve both games.

4. Fun: the reward loop is under-invested, and it's cheap to fix. The biggest miss: the game computes your rating change every round and never shows it to you. apply_round_ratings has the before/after right there, but the reveal says only "2,340 points – 1.2 km away" and the summary is a bare "Game over!" This is half of why you never noticed your rating moving. Showing "▲ +14 rating" on the summary, plus a per-round recap (best/worst guess), an animated count-up on points, and the distance line drawing itself in would transform the feel for a day or two of work — the CSS animation scaffolding already exists. Also: handleInviteMore() uses window.prompt() with the friend list stuffed into the prompt string — genuinely bad UX that should become a real picker. And there's no round-timer option, which is the single most obvious competitive lever (and would double as the fix for the multiplayer stall in #1).

5. The difficulty slider is mostly a placebo for real users. Difficulty weighting only kicks in after a location has 5+ plays; with per-user pin pools, most locations will never get there, so everything sits at the neutral 1500 and easy/medium/hard select nearly uniformly. Seeding location difficulty from proxies the DB already has (boundary size, photo count, how many users pinned it) would make the slider real from day one.

Minor notes: Street View re-fetches imagery through the gateway on every serialize_round (cache-backed, so fine today, but a paid API sits on a broadcast path — worth remembering); named_place.py's getattr(location, "wiki", None) works only because Django's RelatedObjectDoesNotExist subclasses AttributeError — correct but fragile-looking; the session-config JSON snapshot is a good no-migration pattern but is starting to accumulate untyped keys (bonus_scope now lives there too).

My recommendation, in order: fix the multiplayer stall (timeout → auto-reveal or ABANDONED), then the rating-delta/summary reward loop (highest fun-per-effort), then the TS panel-state refactor with a few bun tests, and fold the mode-strategy cleanup into whichever change next touches session.py. Happy to start on any of these — the stall fix and the rating-delta display are each well-scoped enough to do right now.
